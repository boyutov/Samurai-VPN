# UDP relay — версия 0.3

Большинство домашних компьютеров находятся за NAT роутера и не имеют адреса,
доступного из интернета. WireGuard между двумя такими участниками напрямую не
соединится. Для них сервер может работать как relay: он пересылает зашифрованные
пакеты WireGuard, не зная ключей и не видя игровой трафик.

## Как это работает

- Для каждой пары участников, у которых **оба** не указали endpoint, сервер выделяет
  два UDP-порта. Участник A получает endpoint `relay:портA`, участник B — `relay:портB`.
- Клиенту ничего дополнительно запускать не нужно: обычный WireGuard отправляет
  пакеты на этот endpoint, PersistentKeepalive = 25 держит NAT открытым.
- Если хотя бы у одного участника пары указан доступный endpoint, используется
  прямое соединение, как раньше.
- Отзыв участника сразу освобождает его порты: relay перестаёт пересылать его пакеты,
  даже если у других участников ещё старый профиль.

## Защита

- Пересылаются только структурно корректные сообщения WireGuard (типы 1–4,
  точные размеры, нулевые reserved-байты, не больше 2048 байт).
- Адрес отправителя запоминается только после handshake с правильным mac1,
  вычисленным для открытого ключа получателя (BLAKE2s, как в протоколе WireGuard).
  Пакеты данных принимаются только с запомненного адреса. Посторонний, не знающий
  открытых ключей сети, не может перехватить порт.
- Ограничения: 2 МБ/с (всплеск 4 МБ) на направление, 20 проверок handshake в секунду
  на порт.
- Ограничение: открытые ключи известны участникам сети. Участник-злоумышленник может
  занять чужой relay-порт. Это даёт отказ в обслуживании и доступ к шифротексту,
  но не к содержимому. Оператор сервера видит метаданные: кто, когда и сколько.

## Запуск сервера с relay

    ./samurai.sh server --tls-keystore server.p12 --admin-token-file admin.token \
        --bind 0.0.0.0 --port 8787 \
        --relay-host 203.0.113.10 --relay-ports 40000-40199

- `--relay-host` — публичный IPv4 сервера (литерал, без DNS).
- `--relay-ports` — диапазон UDP-портов, 2–2048 штук. Каждая пара занимает два порта:
  200 портов хватает на 100 пар (например, сеть из 14 участников за NAT).
- `--relay-bind` — адрес привязки, по умолчанию 0.0.0.0 (с `--dev` — 127.0.0.1).
- Откройте этот диапазон UDP в firewall сервера и у хостинг-провайдера.

После включения relay участникам достаточно заново экспортировать профиль или
переподключить туннель: новые endpoint придут в списке участников.

## Проверено

- BLAKE2s сверен с RFC 7693 и с Python hashlib; mac1 сверен с независимым вектором.
- Пересылка через настоящие UDP-сокеты на loopback: доставка в обе стороны, ответ
  приходит с порта, указанного в профиле; отказ посторонним адресам, поддельному
  и чужому mac1, не-WireGuard пакетам; прекращение пересылки после отзыва.
- Выдача портов: симметрия пары, стабильность, прямые endpoint не заменяются,
  исчерпание пула, повторное использование освобождённых портов.

## Прямые соединения (hole punching)

Relay видит, с какого публичного адреса и порта приходят пакеты WireGuard каждого
участника: это его отображение в NAT. Сервер передаёт этот адрес другому участнику
пары в поле `candidate` списка участников (только участникам, не владельцу).

Пока окно приложения открыто и установлена служба samurai-vpnd, PathManager каждые
5 секунд проверяет туннель:

1. Попытки начинаются в общих 30-секундных слотах по часам (NTP), поэтому обе
   стороны пробивают NAT одновременно, а не каждая в своё время.
2. Во время попытки endpoint друга переключается на его candidate, и каждые 5 секунд
   на его виртуальный IP отправляется крошечный UDP-пакет. WireGuard шифрует его и
   отправляет на прямой адрес: так каждый NAT открывает «дыру» навстречу другому.
3. Если между двумя проверками пришли байты, а endpoint остался прямым, путь
   работает: пакет через relay вернул бы endpoint на relay (roaming WireGuard).
   Handshake для этого не нужен: после смены endpoint WireGuard продолжает старую сессию.
4. Нет ответа за 25 секунд — возврат на relay. Следующие попытки в слотах кратных
   2, 4, 8… (до 64 слотов, около 32 минут), одинаково на обеих сторонах.
5. На прямом пути нет входящих байтов 60 секунд (keepalive идёт каждые 25 с) или
   друг вернулся на relay — возврат на relay.

При закрытии окна приложение возвращает участников на relay, чтобы туннель не
остался на неработающем прямом пути.

Ограничения: symmetric NAT (часть мобильных и корпоративных сетей) меняет порт для
каждого адресата, с ним остаётся relay. Два участника за одним роутером пока
идут через relay: локальные адреса не публикуются. Роутер, который принимает
непрошеные пакеты на WAN (без фильтра input), сохраняет для раннего пакета друга
запись conntrack, и masquerade меняет порт уже для нашего ответа — такая пара тоже
остаётся на relay. Обычные домашние роутеры такие пакеты отбрасывают. Публичный IP участника виден
другим участникам сети, как в любом P2P.

## Проверка с настоящим NAT

NatTraversalTest строит в изолированных namespaces два клиента за двумя
NAT-роутерами (nftables masquerade, непрошеные пакеты на WAN отбрасываются, как
у домашнего роутера) и relay «в интернете». С настоящим WireGuard
он проверяет: ping через relay, правильные candidate, переход обеих сторон на
прямой путь, а после блокировки прямого пути — возврат на relay с работающим ping.
Запуск и подготовка системы описаны в LINUX.md, «Изолированная проверка»;
сеть компьютера тест не меняет.

**Ещё не проверено:** работа через настоящий интернет и домашние роутеры.
Для этого нужен сервер с публичным IP и два компьютера за разными NAT.
