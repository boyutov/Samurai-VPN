# WireGuard на Windows — версия 0.3 (проверено в CI, не на устройстве)

Код Windows-клиента готов и покрыт тестами, но **ещё ни разу не запускался на
настоящем Windows**. Тесты моделируют ответы sc.exe, wireguard.exe, wg.exe, netsh и
PowerShell. Первая проверка на устройстве описана в конце.

## Устройство

Туннель поднимает официальный WireGuard for Windows (WireGuardNT): для каждой сети
создаётся его служба туннеля `WireGuardTunnel$samurai…`. Своей криптографии и своего
драйвера в проекте нет.

Окно работает от обычного пользователя. Привилегированные операции выполняет
служба Samurai VPN: Java-процесс от имени SYSTEM, который запускает планировщик
заданий при старте системы. Сторонняя обёртка для служб не нужна. Служба принимает
те же операции, что samurai-vpnd на Linux: up, down, status, endpoint, sync.

- Конфигурация туннеля с приватным ключом лежит в `C:\ProgramData\SamuraiVPN\tunnels`.
  Читать её могут только SYSTEM и администраторы. Туннель считается своим, только если
  его конфигурация лежит в этой папке. Чужая служба WireGuard с таким же именем не
  изменяется.
- Окно связывается со службой через AF_UNIX-сокет `C:\ProgramData\SamuraiVPN\run\service.sock`
  (есть в Windows 10 1803 и новее). На Windows ядро не сообщает службе, кто подключился,
  поэтому доступ к сокету по правам на папку получает **один пользователь**, указанный
  при установке.
- Маршруты: WireGuard добавляет /32 к участникам из AllowedIPs. При изменении состава
  сети служба добавляет и удаляет их через `netsh ... store=active`, проверяет результат и
  переписывает конфигурацию, чтобы перезапущенный туннель сохранил состав сети.
- DNS, основной маршрут и firewall не меняются. MTU 1280. Перед подключением служба
  проверяет маршруты и адреса (Get-NetRoute, Get-NetIPAddress) на пересечение с сетью.
- Прямые соединения (hole punching) работают так же, как на Linux: пока окно открыто,
  PathManager переключает endpoint через `wg set`.

## Установка

1. Установите WireGuard for Windows: https://www.wireguard.com/install/
2. Соберите приложение: `mvn verify`, затем `./package.ps1` (получится `dist\SamuraiVPN`).
3. В PowerShell от имени администратора:

       powershell -ExecutionPolicy Bypass -File native\windows\install-service.ps1 -Image dist\SamuraiVPN -User $env:USERNAME

   Скрипт копирует приложение в `C:\Program Files\SamuraiVPN` (запись только для
   администраторов), создаёт папки с правами, регистрирует задание «Samurai VPN Service»
   и ждёт появления сокета.
4. Запустите SamuraiVPN.exe: кнопки туннеля станут доступны.

Удаление (отключает и удаляет только туннели Samurai, сам WireGuard остаётся):

    powershell -ExecutionPolicy Bypass -File native\windows\uninstall-service.ps1

## Первая проверка на устройстве

Нужны два компьютера (или Windows и Linux) и сервер. Проверить и прислать результат:

1. Установка проходит, сокет появляется, в окне нет подсказки «Служба не запущена».
2. «Подключить»: в WireGuard for Windows появился туннель `samurai…`, `ping` до участника идёт.
3. `Get-Acl C:\ProgramData\SamuraiVPN\tunnels | Format-List` — доступ только SYSTEM и Administrators.
4. Другой пользователь Windows не может подключиться к сокету.
5. Новый участник появляется в работающем туннеле без переподключения (`route print 10.203.*`).
6. «Отключить» удаляет туннель и его файл; перезагрузка — служба стартует сама.

Ошибки службы видны в истории задания в Планировщике заданий.

## Что проверяет CI (GitHub Actions, windows-latest)

- Синтаксис install-service.ps1 и uninstall-service.ps1 (парсер PowerShell).
- WindowsSystemTest от администратора с настоящим WireGuard for Windows: служба туннеля,
  ключ, маршруты /32 через netsh, endpoint, sync, удаление службы и файла.
- Запрос маршрутов в очищенном окружении службы укладывается в бюджет команды.

- Полная установка: package.ps1, install-service.ps1 для отдельной учётной записи,
  служба от SYSTEM через планировщик. Эта учётная запись подключается к сокету, другая
  получает отказ доступа. InstalledServiceTest поднимает туннель через установленную службу.
- uninstall-service.ps1 удаляет задание, оставленный туннель и папки; WireGuard остаётся.

CI нашёл и помог исправить: PowerShell без кэша анализа модулей стартовал 35–50 с
(автозагрузка модулей теперь отключена); служба туннеля запускается и удаляется асинхронно
(Samurai теперь ждёт); jpackage удалял runtime\bin\java.exe, без которого служба не запускается.

Не проверены в CI: запуск службы после перезагрузки, окно приложения и трафик между устройствами.
